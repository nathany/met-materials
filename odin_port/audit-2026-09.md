# Code and reading-plan audit — 2026-09-07

Scope: both Odin chapters and their five variants, `common/modelio`, the launcher,
and `Metal-odin-port-plan.md`, compared with the corresponding fifth-edition
Swift pages and the installed dev-2026-09 bindings/Apple SDK headers.

This is a dated audit snapshot. [KNOWN_ISSUES.md](../KNOWN_ISSUES.md) tracks current
disposition and priority, including the reference-implementation criterion and
the subsequent assessment of CodeRabbit's review.

## Remaining code findings

### P2: Failure checks from Swift are missing

Both renderers leave `newCommandQueue`, `commandBuffer`, and
`renderCommandEncoderWithDescriptor` results unchecked. The Swift examples
force-unwrap the queue and guard the command buffer/encoder. With a nil result,
subsequent Objective-C messages can silently do nothing, leaving a blank or
stale window instead of reporting the failure.

Locations: chapter 1 `renderer_init` / `draw` (queue at line 87, command creation
at lines 138–139); chapter 2's corresponding procedures. Restore equivalent
failure checks. Assertions or formatting in `draw` also require establishing an
Odin context because it is a C callback. Continue treating an unavailable
drawable/render-pass descriptor as a skipped frame in the continuous-view shell.

### P2: Vertex-buffer offsets are discarded

Both initializers extract `MTKMeshBuffer.buffer` and cache only the MTLBuffer;
both draw callbacks bind it with offset zero. Apple's MTKModel.h documents that
several MTKMeshBuffers may share one MTLBuffer with distinct offsets. Such a mesh
would read the wrong vertex region. Cache/use `vertex_buffer->offset()`, just as
the code already does for index buffers.

This assumption also appears in the Swift pages. All five tested variants report
vertex offset zero, so this is a latent correctness issue, not an observed image
regression. Explain the small robustness difference when correcting it in Odin.

### P3: Ownership is intentionally bounded by process lifetime

The owned MTKMesh is never released and its owner pointer is discarded. Its
retention keeps the cached borrowed buffers valid, so simply adding a local
`defer mesh->release()` would create dangling pointers after setup. The command
queues, pipelines, shell objects, and retained view-delegate wrappers also lack
an explicit shutdown path; chapter 2 never deletes its dynamic submesh array.

There is no new Odin array allocation or explicit retain in the draw loops, and
their autorelease pools drain each frame. These are bounded lifetime shortcuts
in the current one-shot examples, not evidence of frame-by-frame growth.
Repeated `renderer_init` calls would leak more owners, and chapter 2 would append
to its previous submesh list, so they are not safe reload APIs.

Before reuse, store the owning mesh in `Renderer`, define init/destroy lifetimes,
and delete/reset the submesh array. Keeping MTKMesh and iterating its submeshes
directly would also more closely resemble Swift and avoid the duplicated cache.
Detach/pause the view before renderer destruction, then release the retained
delegate wrapper. Normal AppKit termination can exit without returning from
`app->run()`, so main-scope `defer` calls alone would not solve shutdown.

These source findings are recorded for review; this audit changes documentation
and project guidance, not the demo implementations.

## Things checked that are not bugs

- Chapter 2's branch-local `defer` calls do not free its mesh early: `when`
  introduces no scope. A minimal executable confirmed cleanup after the code
  following `when`; the compiler's `lb_build_when_stmt` emits its statements in
  the enclosing scope.
- The 12-byte imported vertex stride is legal because Model I/O packs the data
  according to the descriptor. It is distinct from shared-struct layout.
- The USDZ imports intentionally select the first MDLMesh, matching Swift; the
  train's six submeshes are retained in the draw list.
- Setup-owned paths use the persistent allocator and are deleted after URL use.
  NSError descriptions are read before their autorelease pool drains.
- The retained NSValue delegate wrapper is necessary with the current vendor
  bridge. Removing it makes the weak delegate disappear after setup.
- The used Model I/O enum values, selectors, vector argument representations,
  and MTKMeshBuffer offset/index types match the installed SDK declarations.

## Verification and limits

Temporary copies of all five demos built with `-vet -strict-style` and ran on
macOS 26.6.2 arm64 with `NSZombieEnabled=YES`, Metal API validation, and Metal
shader validation. Audit-only code waited for three GPU command buffers to
complete after setup pools drained, checked `.Completed`, and terminated the app.
Every variant passed and exited 0. Vertex offsets were zero; submesh counts were
sphere 1, ellipse 1, train 6, cone 1, mushroom 1. No message-to-deallocated-object
diagnostic was observed. The train run emitted a duplicate `_NSZombie_CFReadStream`
class warning under zombie instrumentation; that diagnostic remains a test caveat.

The plan's reference math was compiled and compared numerically against the
book's chapter 10 `MathLibrary.swift`: left/right-handed perspective, left/right
look-at, orthographic projection, and XYZ/YXZ Euler rotations. All seven cases
agreed within 1e-6. Near/far planes mapped to depth 0/1, and both view matrices
mapped the eye to the origin. Swift and Odin size/alignment probes confirmed the
layout differences above. The revised math snippet passes `-vet -strict-style`,
and all local documentation links resolve. These checks supplement the earlier visual verification;
they do not establish leak freedom, arbitrary-asset support, or correctness of
unimplemented chapters. Zombie mode deliberately retains deallocated objects
and is not a memory-usage measurement.
